## 1. 这是什么

MatterTable 把「一个文件夹下所有 markdown 文件的 front matter」显示成一张**多维表格**。表格的每一行是一个 markdown 文件，每一列是 front matter 里的一个属性（字段）。你可以像用飞书多维表格一样，直接在表格里改单元格，改动会写回对应的 markdown 文件，**不需要打开文件**。

它解决的核心问题是：你有几百篇笔记，每篇的 front matter 里有标题、日期、分类、标签、状态，但想「一次性看看哪些笔记还没开始」「按日期排一遍」「把这几篇的分类从 CS 改成 AI」时，只能逐个打开文件改。MatterTable 把这件事变成一张可排序、可编辑的表。

### 名词解释（给非技术读者）

- **front matter**：markdown 文件最上方被两行 `---` 包起来的一段内容，用来存放这篇笔记的元信息。例如：

  ```markdown
  ---
  title: Agent Concepts Introduction
  date: 2026-09-06
  categories:
    - AI
  tags:
    - Agent
  state:
    - not started
  ---
  这里开始是笔记正文……
  ```

- **字段 / 属性**：front matter 里的一个 key，例如 `title`、`date`、`state`。在表格里就是一个列。
- **字段类型**：这个字段的值是什么种类——文本、数字、复选框（勾/不勾）、日期、单选、多选。
- **选项池**：单选/多选字段的候选值列表，例如 `state` 的候选值是「not started / finished」。**选项的先后顺序是有意义的**，因为「按选项顺序排序」要用到它。
- **视图**：表格的一套显示配置（扫哪些路径、显示哪些列、怎么排序、怎么筛选）。MVP 只有一个视图，但配置文件的数据结构已经按「多个视图」设计，后期加视图不用改数据格式。
- **schema / 配置文件**：一个记录「有哪些字段、每个字段什么类型、选项池是什么、显示哪些列」的 JSON 文件（见 §5.2）。

## 2. 目标与非目标

### 2.1 MVP 目标（必须做到）

1. 在 Cursor 里用一个标签页打开一张表格，看到指定路径下所有 markdown 文件的 front matter 字段。
2. 能直接改单元格（文本 / 数字 / 复选框 / 日期 / 单选 / 多选），改完立刻写回文件。
3. **写回是安全的**：只改该字段对应的字节，文件其余部分（换行符、BOM、引号风格、注释、缩进）逐字节不变；任何有风险的情况（文件正在被编辑、外部已改动、front matter 本身是坏的 YAML）都拒绝写入并提示。
4. 文件名列只读、点击在新标签页打开该文件。
5. 列可以隐藏/显示、可以拖动排序、可以拖动改宽度，配置被记住。
6. 支持单列排序（日期、文本、单选按选项顺序、数字、复选框）。
7. 没有 front matter 的文件默认不显示；提供一个按钮给它们一键补上 front matter 骨架。

### 2.2 MVP 明确不做（放到后续版本）

| 功能 | 计划版本 |
| --- | --- |
| 筛选条件（日期等于今天、分类等于 CS 等） | v2 |
| 多个视图（每个视图独立筛选/列/排序/命名） | v2 |
| 日历视图 | v2 |
| 选中多行、批量把某字段改成同一个值 | v2 |
| 在表格里新建文件 / 删除文件 | v2 |
| 重命名字段（批量改全库的 key 名） | v2 |
| 从 Excel / 飞书粘贴数据导入 | **不做**（用户明确不要） |
| 云端同步、协作、账号 | 不做（纯本地） |
| 编辑嵌套对象字段（如 `hero: {...}`、`sitemap: {...}`） | 不做（只读或隐藏） |

## 3. 使用场景

1. **通览与排期**：打开表格 → 按 `state` 或 `date` 排序 → 找出还没开始的笔记 → 直接在表里改状态。
2. **批量整理元信息**：发现某一列的分类写错了，在表里逐个改掉，不用打开 20 个文件。
3. **日期校准**：把一批笔记的 `date` 改成发布日期。
4. **补齐缺失字段**：对没有 front matter 的笔记点「补骨架」，一次性生成 `title / date / categories / tags / state` 五个字段的框架。

## 4. 数据模型

### 4.1 行与列

- **一行 = 一个 markdown 文件**，行的唯一标识是「相对于扫描根目录的路径」。
- **列 = 一个 front matter 字段**。另外有一个特殊列「文件名」，永远存在、永远在第一位、**只读**。
- 单元格的值 = 该文件 front matter 里该字段的值；字段不存在时单元格为空。

### 4.2 支持的字段类型

| 类型 | UI 控件 | 底层 YAML 值 | 写入规则 |
| --- | --- | --- | --- |
| `text` | 单行输入框 | 字符串 | 按原样写入；含 `: `、`#`、首尾空格等特殊字符时自动加引号（见 §6.4） |
| `number` | 数字输入框 | 数字 | 只接受数字；输入非数字则拒绝并回退（不写入） |
| `checkbox` | 勾选框 | `true` / `false` | 单击在真/假之间切换；右键菜单「设为空」可清空回 null |
| `date` | 日期选择器（Chromium 原生 `input[type=date]`） | `YYYY-MM-DD` | 统一写成不加引号的 ISO 日期 |
| `select` | 可搜索下拉框，支持「新建选项」 | 默认：单项列表，如 `state:\n  - finished`；可选 `scalar` 模式写单个字符串 | 显示为单个标签；写入按 `storage` 设置决定形态 |
| `multiSelect` | 标签输入框（chips） | 列表，如 `tags:\n  - Agent` | 写入保留原有列表风格（块状/行内） |

**重要：`select` / `multiSelect` 底层都用列表存储。** 你是这样要求的，而且你现有的文件本来就是这个风格（实测 `state` 字段在 228 个文件里全部是「单元素列表」写法）。所以：

- `select` + `storage: "list"` → 显示成一个标签，写回时写单项列表（保持你的文件风格不变）。
- `select` + `storage: "scalar"` → 写单个字符串（给明确想要 `state: finished` 这种裸值的字段用）。
- `multiSelect` → 固定写列表，支持多个值。

### 4.3 字段类型的来源（回答「schema 是硬性写入还是打开时扫描」）

**两者都有，但顺序是「先扫描、后固化」，不存在硬性写死。**

1. **类型必须由配置声明**。原因是实测你的库里「数字」只出现过 2 次、「布尔」只出现过 5 次，靠自动推断根本得不到这两类字段；字段叫 `Date` 还是 `UpdateDate` 也无法从数据里猜出你的意图。
2. **选项池是打开表格时自动扫描收集的**（你确认过这是你想要的行为）：扫描范围内所有文件，把每个 `select`/`multiSelect` 字段出现过的不同取值收集起来。
   - 如果配置里这个字段的 `options` 是空数组 `[]` → 表示「自动模式」：所有扫描到的值都算合法选项，按「出现次数从多到少、次数相同按名称」排序。
   - 如果配置里手写了 `options` 列表 → 表示「手动模式」：这个列表就是正式选项及其顺序，**未在列表里的值依然正常显示（标一个淡淡的「未定义」提示），但不会被自动加进选项池**，你可以点「加入选项池」手动收编。
   - 这样设计的目的：既不需要你预先配置就能立刻用，又不会让某个笔误（比如 `Agetn`）自动污染选项池。
3. **配置里没提到的字段也会自动出现**：扫描时发现配置里没有的字段（例如别人仓库带来的 `author`、`source`），类型按值推断（字符串→文本、数组→多选、数字→数字、真/假→复选框、日期→日期），列排在最后并默认可见，你可以手动改类型或隐藏。
4. **改配置的方式（MVP）**：命令面板里 `MatterTable: 打开配置文件`，直接编辑 JSON。字段顺序、类型、选项池、列宽都在里面。MVP 不做图形化的字段管理面板。

### 4.4 不支持的字段（嵌套结构）

YAML 允许「字段的值又是一个对象」或「列表里装对象」，例如第三方仓库文档里的：

```yaml
hero:
  name: Vibe Vibe
  text: 人人都能 AI 创造
sitemap:
  changefreq: weekly
```

这类字段（含「列表里装对象」，如 `features`、`actions`、`head`）在 MVP 中的处理：

- **默认隐藏**，不出现在表格里。
- **只有在配置里显式给该字段写 `visible: true`** 时才会作为一列出现，且为只读（单元格显示「（嵌套结构，只读）」，hover 显示字段名）。填值、改值一律被拒绝（写入器会直接报 `FIELD_COMPLEX`）。
- **不能由视图的 `hiddenColumns` 决定**：`hiddenColumns` 只负责普通字段的显隐。原因是嵌套字段往往是外部仓库带来的噪音，如果交给视图状态决定，每发现一个新的嵌套字段就会自动多出一列。

- 理由：编辑它们需要递归修改 YAML 结构，风险高、收益低；而且这些字段主要来自你下载的第三方仓库，不是你的个人笔记。
- 补充：默认忽略清单（§5.1）已经把 `20 Raw/`、`30 Raw/` 排除，所以正常情况下你根本看不到它们。

### 4.5 空值语义（回答「删掉内容到底怎么存」）

你希望「把内容删了就设为空」。MVP 的规则是**按字段类型决定「空」的写法**，并且可以选择风格：

| 情形 | 默认写法 | 说明 |
| --- | --- | --- |
| 文本 / 数字 / 日期，清空 | 保留 key，值留空：`title:` | 和你模板里的写法一致（实测你的库里就有 138 个 `title:`、142 个 `date:` 是这种空值形式）。好处：字段不会消失、以后填回来不用重新打字，博客按字段名取值时也不会因为「字段不存在」报错。 |
| 单选 / 多选，清空 | `state: []` | 空列表，语义最清楚。 |
| 复选框，清空 | 保留 key，值留空：`published:` | 表示「未设置」，区别于明确的 `false`。 |

补充：如果列表里只有空项（文件里写的是 `categories:` 换行 `  - `），表格把它显示成空，写入时规范成 `categories: []`。审计显示你的库里有 12 处这种写法，同样**只有你手动改那些单元格时才会发生**。

配置项 `settings.emptyValueStyle` 可改：

- `"null"`（默认）→ 如上表，写空的 key。
- `"remove"` → 直接删掉整个 key 行。
- `"emptyString"` → 写成 `title: ""`。

### 4.6 日期与引号风格（统一口径）

- **日期统一写成不加引号的 `YYYY-MM-DD`**，例如 `date: 2026-09-06`。理由：这是你现有笔记的主流写法（实测未加引号 54 个、加引号 73 个，两种写法 Astro/Vite 内容集合都能解析，但统一后排序和筛选不会出错），同时避免不同工具把它改写成 `2026-09-06T00:00:00.000Z` 这种带时区的长串。
- **引用风格的现实约束**：因为写入是「行级最小改写」，一个**已经存在**且带引号的值（`date: '2026-03-07'`）在你不动它时会原样保留引号；一旦你改了这个单元格，它就变成统一的「不加引号」写法。这属于可接受的一次性收敛。
- **不需要「日期+时间」类型**（你确认过）。你库里 `created_at` / `updated_at` 那种带毫秒的时间戳会被当成**文本**处理，只读展示。

## 5. 扫描范围（回答「路径能不能让用户自己选」）

### 5.1 规则

1. **扫描根目录可选**：默认是当前工作区根目录（也就是你打开 Cursor 时的 `D:\KnowledgeBase`），可以在配置文件里改成任意绝对路径。MVP 只支持一个根目录。
2. **递归扫描**子目录下所有 `.md` 文件。
3. **默认忽略清单**（可在配置里改）：

   ```json
   ["**/node_modules/**", "**/.git/**", "**/.trash/**", "**/.obsidian/**", "**/.mattertable/**",
    "**/20 Raw/**", "**/30 Raw/**", "**/.helloagents/**", "5 Projects/**"]
   ```

   每一项为什么在清单里：

   - `**/20 Raw/**`、`**/30 Raw/**`：实测这两个目录下有 **614 个** markdown，全是 hello-algo、javaguide、vibevibe、hello-agents、learn-claude-code 等第三方仓库克隆的文档，不是你自己的笔记。不排除的话表格里 70% 是别人的文档。
   - `**/node_modules/**`、`**/.git/**`、`**/.trash/**`：依赖包和版本控制内部文件，没有管理价值。
   - `**/.mattertable/**`：MatterTable 自己的配置与备份目录。
   - `**/.helloagents/**`：实测有 3 个文件的 front matter 是**非法 YAML**（`title: 发现问题: 你好...`，冒号没转义），是别的工具写的，排除掉省心。
   - `5 Projects/**`：这里放的是**代码项目**，包括 MatterTable 扩展自己的源码（就是本仓库，里面会有 `README.md`、本 PRD 等 markdown）和 BornfreeYan 博客仓库（里面是已发布文章的副本，会和你的源笔记重复出现）。不排除会看到「同一篇笔记出现两行」。

   配置里支持「路径关键词排除」，也就是上面这种 glob 写法；`**/关键词/**` 就能排除任何层级下名字含该关键词的目录。后续版本会在 UI 里提供一个编辑界面，MVP 直接改 JSON。
4. **是否遵循 `.gitignore`**：不做（你的库不是 git 仓库，且默认清单已经覆盖）。

### 5.2 配置文件 `.mattertable/config.json`

位置：**工作区根目录**下的 `.mattertable/config.json`（用 Cursor 打开哪个目录，配置就放在那里）。至于「扫哪个目录」由配置里的 `scope.root` 决定，默认就是工作区根目录，也可以写任意绝对路径（例如你打开 `D:\mattertable-test` 当工作区、却想管理 `D:\KnowledgeBase`）。

> 实现说明：最初的设计是「配置放在扫描根目录下」，但那样会形成循环依赖——扫描根要由配置决定，配置又放在扫描根里。改成放在工作区根后就没有这个问题了。配置文件**不在扩展代码仓库里**，跟库/工作区走。


```json
{
  "version": 1,
  "scope": {
    "root": "D:/KnowledgeBase",
    "include": ["**/*.md"],
    "exclude": [
      "**/node_modules/**",
      "**/.git/**",
      "**/.trash/**",
      "**/.mattertable/**",
      "**/20 Raw/**",
      "**/30 Raw/**",
      "**/.helloagents/**",
      "5 Projects/**"
    ]
  },
  "settings": {
    "emptyValueStyle": "null",
    "dateFormat": "YYYY-MM-DD",
    "unparsableFilesPolicy": "readonly"
  },
  "fields": [
    { "key": "title",      "type": "text",        "label": "标题",  "width": 260, "visible": true, "order": 1 },
    { "key": "date",       "type": "date",        "label": "日期",  "width": 130, "visible": true, "order": 2 },
    { "key": "categories", "type": "select",      "storage": "list", "label": "分类", "options": ["CS", "AI", "English", "Life"], "width": 150, "order": 3 },
    { "key": "tags",       "type": "multiSelect", "label": "标签",  "width": 220, "visible": true, "order": 4 },
    { "key": "state",      "type": "select",      "storage": "list", "label": "状态",  "options": ["not started", "finished"], "width": 130, "order": 5 },
    { "key": "description","type": "text",        "label": "摘要",  "width": 280, "visible": false, "order": 6 }
  ],
  "skeleton": {
    "fields": ["title", "date", "categories", "tags", "state"],
    "autoFillDateToday": true,
    "stateDefault": ["not started"]
  },
  "views": [
    {
      "id": "default",
      "name": "全部笔记",
      "type": "table",
      "sort": [],
      "hiddenColumns": ["description"],
      "columnOrder": ["title", "date", "categories", "tags", "state", "description"],
      "columnWidths": {}
    }
  ]
}
```

说明几点：

- `views` 数组 MVP 只用第一个（`id: "default"`），但格式已经按「多视图」设计——v2 加视图只是往数组里追加对象，不需要数据迁移。后期你会看到的是「一个视图专门展示 CS、一个专门展示 AI、一个用日历视图展示任务、各自可命名」。
- 排序状态 `sort` 也是数组形式（`[{ "key": "date", "direction": "desc" }]`），MVP 只支持一项，但格式支持后期多级排序。
- 配置文件被改动后，表格自动重新加载（会监听这个文件）。

## 6. 写入器：怎么安全地改文件（核心设计）

这是整个插件风险最高、也最关键的部分。原则是：**除了你改的那个字段，文件里其他字节必须一个都不变。**

### 6.1 写入流程

1. 读文件原始字节，记录：是否有 BOM、换行符是 CRLF 还是 LF、文件修改时间、大小、内容 SHA-1。
2. 确认文件以 `---` 开头（允许前面有 BOM）。不是 → 该文件没有 front matter，若你要写值，走「补骨架」流程（§7）。
3. 用 `yaml` 库的 `parseDocument` 解析 front matter 内容，拿到每个字段在文本里的**精确字符位置**（起止偏移量）。解析失败 → 该文件标记为「无法解析」，**只读**。
4. 定位要改的字段：
   - **值已存在** → 只替换「值」那一段字符（保留缩进、列表符号、原有引号）。
   - **值是空的**（如 `date:` 后面没内容）→ 把值那段（外加它下面属于它的缩进块）替换成新值的正确写法。
   - **字段不存在** → 在 front matter 块的最后一行之后插入一行（或一个列表块），缩进与文件内其他字段保持一致。
5. 用「文件前缀 + 改写后的片段 + 文件后缀」拼回完整内容——**其余字节完全没被touch过**。
6. 写入前的最终校验：重新读一次磁盘上的文件，比对第 1 步记录的「修改时间 + 大小 + SHA-1」。三者有一个不一致 → **中止写入**，提示「文件已被外部修改，表格已刷新，请重试」。
7. 如果该文件正在某个编辑器里打开且**未保存**（dirty）→ 中止写入，提示先保存。
8. 写入方式：优先用 VSCode 的 `WorkspaceEdit`（这样 VSCode 自己会记录这次改动，编辑器里能看到 diff）。**同时**在内存里保留这次改动前的原文，提供命令 `MatterTable: 撤销上一次改动`（本次会话内有效）作为兜底。
9. 写完后把新值、新修改时间、新 SHA-1 更新进缓存，只刷新表格里这一行的这一个单元格。

### 6.2 一个具体的例子

原文件（CRLF 换行，注意 `state` 是块状列表）：

```markdown
---
title: Agent Concepts Introduction
date: 2026-09-06
state:
  - not started
---
（正文）
```

把 `state` 改成 `finished`，写入结果是：

```markdown
---
title: Agent Concepts Introduction
date: 2026-09-06
state:
  - finished
---
（正文）
```

只有 `  - not started` 这一行的 `not started` 部分被替换。`title` 行、`date` 行、CRLF 换行符、`---` 的个数、正文，全部原样未动。

### 6.3 无法解析的文件（降级策略）

实测你的库里有 3 个文件的 front matter 本身是非法 YAML（值里出现了未转义的冒号）。对这类文件：

- 文件仍然出现在表格里，但**整行只读**（所有单元格灰掉、不可编辑）。
- 单元格 hover 显示具体错误信息（哪一行、什么错）。
- 提供「跳到出错的行」动作，方便你去修。
- **写入器对该文件直接拒绝**，绝不尝试修复或重写。

### 6.4 文本值的引号规则

写入文本时判断是否需要引号，避免写出坏 YAML：

- 需要引号（写双引号）的情况：值里含 `: `（冒号加空格）、以 `- ` 或 `#` 开头、含 `"` 或 `\`、首尾有空格、值是 `true/false/null/yes/no` 这类会被 YAML 当成布尔的词、看起来像数字但你想当文本（如 `version: "1.0.0"` → 这里 `version` 若声明为 text 则加引号）。
- 其他情况不加引号，保持文件干净。

### 6.5 注释怎么处理

- **字段行尾的注释会保留**：`title: 旧值 # 备注` 改成 `title: 新值 # 备注`。
- **列表块内部某一项的行尾注释，在重写这个列表时会被上移到字段行**：例如

  ```yaml
  state:
    - not started # 状态
  ```

  在改成 `finished` 之后变成

  ```yaml
  state: # 状态
    - finished
  ```

  内容不丢，只是位置从项目行移到了字段行；同一个列表块里有多个注释时只保留最后一个。

## 7. 一键补骨架

对「没有 front matter」的文件（实测你的库里有 **442 个**）：

- 默认**不显示**在表格里（否则表格一半是空行）。
- 表格顶部有一个开关「显示没有 front matter 的文件」，打开后这些文件显示为空行（文件名列照常，其他列空白）。
- 这些行提供一个行级动作「补骨架」，点击后在文件**最开头**插入：

  ```markdown
  ---
  title:
  date: 2026-09-13
  categories: []
  tags: []
  state:
    - not started
  ---
  ```

  其中 `date` 是否自动填今天、`state` 的默认值、要补哪些字段，都由配置里的 `skeleton` 决定。
- 插入时同样遵守字节保真规则：BOM 保留、原有换行风格（CRLF/LF）沿用、正文一动没动。如果文件本来不是以 `---` 开头的普通 markdown，插入后要让 `---` 块之后紧接一个空行再接正文。
- 「补骨架」也是一次可撤销的写入（同上，进撤销栈）。

### 8.3 排序规则

| 字段类型 | 升序 | 降序 | 空值位置 |
| --- | --- | --- | --- |
| 日期 | 早 → 晚 | 晚 → 早 | 永远排最后 |
| 文本 | A → Z（中文按拼音，使用 `Intl.Collator("zh")`） | Z → A | 永远排最后 |
| 数字 | 小 → 大 | 大 → 小 | 永远排最后 |
| 单选 | 按选项池顺序（池中第一个最小） | 倒序 | 未定义的值、空值排最后 |
| 多选 | 取该行「选项池序号最小的那个值」参与比较 | 倒序 | 同上 |
| 复选框 | 未勾 → 已勾 | 已勾 → 未勾 | 空值排最后 |

补充规则：排序必须**稳定**——两个文件该字段相等时，按文件名升序决定先后，避免每次刷新顺序乱跳。文件名列默认升序。

### 8.4 自动刷新与冲突

- 监听扫描范围内的文件变化（外部工具写入、git 切换分支、你自己在编辑器里改了保存）。变化发生后延迟 300 毫秒（合并连续变化）刷新受影响的行。
- 如果被外部修改的文件正好是你正在编辑的单元格 → 不覆盖你的输入，提示「该行已被外部修改，请确认」。
- 手动刷新按钮始终可用。

### 8.5 每次会话不需要你关心的事（回答你的疑问）

你问「是不是只要保证打开视图或更改时其他文件都已经 Ctrl+S 过或者关闭就可以了」——**基本正确，但你不用刻意保证**：

- 扩展会**自动检测**：文件还在编辑器里且有未保存内容、或文件在你打开表格之后被别的程序改过，它会主动拒绝这次写入并给你提示，不会静默覆盖。
- 你平时正常操作（改完就保存、或者开着不管）都不会出问题；唯一会被拒绝的情况是「你正在编辑某个文件还没保存，同时又在表格里改同一行」——这时它会提示你先保存。
- 每次写入都会在内存里留一份改动前的原文，`MatterTable: 撤销上一次改动` 命令可以把上一次表格改动整个撤回（本次会话内有效）。你的库不是 git 仓库、你也不需要额外备份，这一层就够用了。
- 所有动作都会记进一个输出面板：`MatterTable: 显示日志（排查问题用）`。里面能看到「扫描完成：… 259 个文件，耗时 450 ms」以及每次「写入成功 / 拒绝写入 + 原因」。测试阶段遇到任何不对劲，先看这个日志。

### 9.3 前后端通信

Webview 与扩展宿主之间只通过消息通信，消息定义集中在 `src/shared/protocol.ts`：

- 宿主 → UI：`init`（字段定义 + 视图配置 + 首批行数据 + 统计）、`rowsChunk`（分批补充行，每批 500 行）、`rowsUpdated`（增量替换若干行，可选删除）、`fieldsUpdated`（只换字段定义，例如选项池多了新值，不动行数据与界面状态）、`viewUpdated`（只换视图配置，例如重置列宽）、`notice`（提示条）、`cellResult`（某次写入的权威结果，失败时界面回退单元格）。
- UI → 宿主：`ready`、`setCell`、`clearCell`、`addOption`、`addSkeleton`、`openFile`、`openConfig`、`refresh`、`setSort`、`setColumnVisible`、`setColumnOrder`、`setColumnWidth`、`resetColumnWidths`、`toggleShowWithoutFrontmatter`。

> 设计要点：凡是**界面自己能算出来的**（排序、列宽、列顺序、列显隐），宿主只负责持久化到配置，不回传数据；只有**界面算不出来的**（重新扫描出的行、字段定义、视图重置）才回传。这样避免「点一下列头，表格跳回顶部、选中丢失」这类问题——v0.1.0 就犯过这个错。

### 9.4 依赖清单（回答「是否需要这些 npm 包」）

包管理用 **pnpm**（你机器上已有）。分两类：

**A. 运行时依赖**（会被打包进扩展，用户不需要手动装任何东西）：

| 包 | 用途 | 是否必须 |
| --- | --- | --- |
| `yaml` | 解析 front matter 并拿到每个字段的精确字符位置——行级最小改写全靠它 | **必须** |
| `react` + `react-dom` | 写 webview 界面（表格、单元格编辑器） | **必须**（除非改用原生 JS，代码会难维护很多） |

**B. 开发依赖**（只在你开发/打包时用，不进扩展包）：

| 包 | 用途 |
| --- | --- |
| `typescript` + `@types/vscode` + `@types/node` | 类型检查；`@types/vscode` 提供 `vscode` 模块的类型（扩展 API 由 Cursor/VSCode 自己提供，不需要安装） |
| `@types/react` + `@types/react-dom` | React 的类型 |
| `esbuild` | 一个工具同时打两个 bundle：宿主侧 CJS + 界面侧 IIFE（界面被打成单个自包含文件，由面板直接注入 HTML）。原计划界面用 vite 打，实测没必要——不需要资源路径处理，也不需要 HMR，少一个工具链就少一类构建故障。 |
| `vitest` | 单元测试。**写入器必须重点测**——你库里的 CRLF、BOM、带引号日期、块状列表、非法 YAML 都会做成测试用例，保证「除了目标字段，其他字节不变」 |
| `@vscode/vsce` | 打包成 `.vsix` 安装文件，用来装到 Cursor 里 |
| `eslint` + `prettier` | 代码风格检查与格式化（可选，建议加） |

**C. 明确不需要的包（以及为什么）**：

| 不装 | 原因 |
| --- | --- |
| `gray-matter` / `js-yaml` | 解析 YAML 时**会丢掉注释和原始格式**，无法做行级最小改写。用 `yaml` 替代。 |
| `fast-glob` / `globby` | Cursor/VSCode 自带 `workspace.findFiles`，自带忽略规则支持，不用额外装。 |
| `chokidar` | Cursor/VSCode 自带文件监听 `createFileSystemWatcher`。 |
| `axios` / `node-fetch` | 纯本地运行，没有任何网络请求。 |
| Ant Design / Element Plus 等组件库 | 体积大（几百 KB 到 MB），而我们需要的表格是自绘的，引入收益低。 |
| `@tanstack/react-table` | 排序规则是我们自己定的（单选要按选项池顺序、空值与「不在选项池里的值」永远排最后、并列时按文件名），用现成表格库反而要绕开它的比较器；自己写的排序逻辑只有 60 行且有单测覆盖。 |

**pnpm 的一个坑（会提前处理）**：pnpm 10 默认禁止依赖运行安装脚本，而 `esbuild` 需要下载平台二进制。所以 `pnpm install` 之后要执行一次 `pnpm approve-builds` 放行 esbuild（或者用 `onlyBuiltDependencies` 配置声明）。这一步我会在搭建项目时一并配好。

### 9.5 性能设计

按 5000 个文件的上限设计（你库里的有效文件目前是 258 个）：

- 只读文件开头的 front matter 区域（不必读整个正文，大文件也只读前几 KB）。
- 增量缓存：以「路径 → {修改时间, 大小, 解析结果}」建索引，存在扩展的全局存储里；下次打开表格时只重新解析变过的文件。
- 行数据分批传给界面（每批 500 行），表格用虚拟滚动（只渲染可见的几十行）。
- 界面渲染与文件写入都做防抖/节流，避免连续编辑时卡顿。

| 风险 | 影响 | 对策 |

## 15. 实现差异与决策记录

（v0.1.0 首版 + v0.1.1 修 bug 后的最终状态）

写代码过程中对本文档做过这些修正，都是实现时才发现更合理的做法：

1. **配置文件位置从「扫描根目录」改为「工作区根目录」**。原因见 §5.2 的说明（避免循环依赖）。带来的实际影响：如果工作区和被管理的知识库不是同一个目录，就用 `scope.root` 指过去。
2. **不用 vite，改用 esbuild 一个工具打通两边**。界面被打成单个自包含的 IIFE bundle，由面板直接注入 HTML，不需要资源路径处理，也不需要 HMR，少一个工具链就少一类构建故障。
3. **不引入 `@tanstack/react-table`**。排序规则是本项目自己定的（单选按选项池顺序、空值与「不在选项池里的值」永远排最后、并列时按文件名），用现成表格库反而要绕开它的比较器。实际排序逻辑只有 60 行，且有单测。
4. **「不在选项池里的值」永远排最后这条规则同时适用于多选**。原文 §8.3 只对单选写了这条，实现时统一到单选+多选（行为更一致：未定义的脏值不会因为切换升降序而跑到最前面）。
5. **列显隐的权威来源是 `views[0].hiddenColumns`**，`fields[].visible` 只在第一次运行时作为初值被固化进去。这样避免「配置里两个地方都能控制显隐、以哪个为准」的歧义。首次运行会把 `visible: false` 的字段写进 `hiddenColumns`。
6. **列头右键简化为「隐藏此列」**，原计划的「按此列排序 / 列宽自适应」菜单项去掉了：排序点列头即可，列宽恢复放在字段面板的「重置所有列宽」。
7. **新增两个原文档没写的东西**：`MatterTable: 显示日志` 命令（排查问题用）与行缓存落盘（记录在 VSCode 全局存储里，靠「修改时间 + 大小」判断是否需要重新解析，让重复打开表格更快）。
8. **列表里只有空项（`- `）会被规范成 `[]`**，原文只说了「空列表写成 `[]`」。这是审计真实数据时发现的：你库里有 12 处这种写法，如果按原逻辑写会触发「写入后校验失败」。
9. **`date: ""` 这类空字符串日期会写成 `date:`（空值）**，属于 `emptyValueStyle: "null"` 的既定行为，审计里 33 处。

### 15.1 v0.1.1 修复的界面 bug（第一次人工测试发现）

这一轮暴露的问题值得记下来，因为**根因只有两个，症状却有五个**：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 文本 / 数字 / 日期列整列空白（只有单选、多选能显示） | 单元格展示逻辑写成「标签数组为空 → 渲染空内容」，而文本类字段的标签数组恒为空，值被吞掉 | 展示逻辑按字段类型分支：列表类走标签，其余直接输出文本 |
| 列错位、单元格被压成一个 0 宽的小框 | 非编辑态外面多包了一层 div，内层 `.td` 没拿到列宽 | 去掉外层包装，由 `Cell` 自己按列宽渲染 `.td` |
| 下拉面板出现在页面左上角 | 进入编辑时 React 替换了单元格 DOM，代码里持有的是已被卸载的旧元素，`getBoundingClientRect()` 全 0 | 展示态与编辑态渲染**同一个** div（元素不被替换），锚点始终有效；并随滚动/缩放重新定位 |
| 多选里输入的新标签会丢 | 每次「加入选项池」都触发整表重载，把未提交的输入冲掉（单选因为是回车即写盘才幸免） | 新增选项只回传字段定义（新消息 `fieldsUpdated`），不重载表格；多选每加一个标签就立刻写盘 |
| 数字列输入非数字没有任何反馈 | 用了 `<input type="number">`，浏览器直接吞掉字母，校验代码永远走不到 | 改成文本输入 + 自己校验，给出「不是合法数字」的明确提示 |
| 「选中单元格后按 Delete 清空」这条路走不通 | 单击就直接进编辑，用户几乎没有「已选中但未编辑」的状态 | 改成电子表格习惯：单击只选中（2px 高亮框），再单击 / 双击 / 回车 / F2 才进入编辑 |
| 嵌套结构字段「默认隐藏」失效 | 列显隐唯一看视图的 `hiddenColumns`，而嵌套字段不在里面，于是 `hero` / `sitemap` / `features` 变成了真实存在的列（只是横向滚出屏幕，测试时被误判为通过） | 嵌套结构字段的显隐与视图状态解耦：默认不显示，只有配置里显式写 `visible: true` 才作为只读列出现 |
| PRD 承诺的「拖动列头调整列顺序」没实现 | 协议里有 `setColumnOrder`、宿主也会持久化，但界面没有拖拽入口 | 补上 HTML5 拖拽（文件名列固定最左），并在拖动列宽时临时关闭列头拖拽，避免两个手势打架 |

同时顺手去掉两处会重置界面的整表回传：列头排序（界面已自行排序，只需持久化）与「重置所有列宽」（改为只回传视图配置 `viewUpdated`）。

**测试策略上的教训**：这一轮之前只有单元测试与集成冒烟测试，两者都不渲染 DOM，所以上面这些问题一个都没抓到。v0.1.1 补了 jsdom 组件测试，到 v0.1.2 共 22 个，其中 6 个是直接针对上述回归的用例。

**另一个教训**：嵌套字段那条属于「PRD 写了、实现里被另一条规则悄悄覆盖」——「人工测试通过」其实是横向滚动没看到。凡是两条规则都能决定同一件事（这里是「视图 hiddenColumns」和「字段 visible」），就必须明确哪一条权威，并且用测试把它钉住。
